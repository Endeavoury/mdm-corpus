Typical scenario

• Publisher publishes successfully for System 1.

• Publisher gets request to publish on System 2.

• Publisher tries with existing data on System 2 but fails.

• Publisher add extra value to satisfy System 2 but the publishing on both
  Systems fails.


→ The codelist restriction is not additive.
Two interpretations for mandatory codelist

Interpretation 1: The value space is closed under the codelist.
Interpretation 2: At least 1 value from the codelist.

Interpretation 1
    • Cardinality and value space constraints are independent.
    • Restricts the freedom of compatible (sub)profiles to reenforcing the
      cardinalities or further restricting the possible codelist values (e.g. to a single
      value).

Interpretation 2
    • Cardinality and value space constraint are made dependent.
    • Compatible (sub)profiles may freely add other codelist constraints.
    • Cannot be used in case the property is optional (cardinality 0 means optional).
Application assessment

• Interpretation 1:
    • Conformant to the way literal value spaces are expressed.
    • Most naturally for programming languages and most software systems.

• Interpretation 2:
    • Of interest in cases where there is a need for aggregation (at the level of
      properties) in the specification.
Validation assessment

• Interpretation 1:
    • Existing SHACL shapes can be used as-is:
       • Validation is simple and direct.
   • As it is closing the value space, violations drive the feedback.

• Interpretation 2:
    • Existing SHACL shapes cannot be used as-is:
       • requires to define a filtering process as inherent part of the processing and conformance
         building Such filtering process is non-trivial to standardise and imposed in all
         implementations.
   • As it is not closing the value space, poor usages will be harder to detect.
   • Matching SHACL shapes can be designed.
Cross-profile assessment

• Interpretation 1 is more strict than Interpretation 2.
   o e.g.: When profiles DCAT-AP use Interpretation 2 and GeoDCAT-AP uses Interpretation 1
     then the usage in DCAT)AP is also Interpretation 1.


• As datasets are subject to multiple profiles, profiles influence each other.
   o e.g.: mobilityDCAT-AP and healthDCAT-AP are siblings, but may influence eachother because
     there are datasets that are expressed under both profiles.


• note that this kind of influence is not limited to codelist constraints but also for
  other constraints such as max-cardinality constraints

• Conclusion: coordination is required.
Proposal: make the interpretation explicit
   A) The property MUST use as range values codes from {codelist}
     = interpretation 1: The value space is closed under the codelist (validation results: violations)
      All (sub)profiles must avoid conflicts by creating subproperties.


   B) The property MUST have at least one value from {codelist}
     = interpretation 2: The value space is minimally constrained (validation results: warnings)
       All (sub)profiles must adopt this interpretation in case they want to restrict the value space.


   C) The property IS RECOMMENDED to use as range values codes from {codelist}
     = interpretation 1: The value space is closed under the codelist, but other values are tolerated (validation
   results: warnings)


   D) The property MAY use as range values codes from {codelist}
    = interpretation 1: The value space is closed under the codelist, but other values are accepted (no
   validation required)

MUST or AT LEAST 1 for dataset theme #316
Description
• In the individual usage notes for dataset theme, the at least 1 formulation is used.
• In the codelist section the must formulation is used.


• In the practice many data portals have aligned with the EU NAL dataset theme vocabulary
    o By extending it
    o By mapping to it (e.g. INSPIRE)
                                                                                                                     Feedback requested
MUST or AT LEAST 1 for dataset theme #316
Proposition A - MUST
All other DCAT-AP profiles that would like to share their theme must introduce a subproperty of dcat:theme.
dcat:theme stays paired exclusively with the EU NAL Dataset theme Vocabulary.
Conflict stays with profiles beyond EU boundaries.
Bug fix release of the specification

Proposition B - AT LEAST 1
All data Catalogues must adapt their uniqueness expectation in the theme property and implement a filter based on
the theme they like to show in the UI.
The used codelists MUST be published as proper Linked Data in the public space. To facilitate every portal to make
easy decisions.
Bug fix release of the specification

Proposition C - Conflict free resolution
Replace the use of dcat:theme in DCAT-AP with a subproperty of dcat:theme.
The new property r5r:theme stays paired exclusively with the EU NAL Dataset theme Vocabulary.
Minor release of the specification.

Relaxation cardinality property dct:rights
(#370 derived from #82 GeoDCAT-AP) + #380
Description
In DCAT-AP dct:rights is used for Catalogue and Distribution, with cardinality 0..1.
In GeoDCAT-AP, the cardinality was relaxed to 0..*.
In DCAT-AP HVD, dct:rights with cardinality 0..* is uses also for Data Services.
Motivation
• Relaxation to 0..* was done for GeoDCAT-AP, to function as a fallback mechanism where multiple
  statements are present, but concatenating them into one value is not desirable.



Proposition

Relax cardinality for dct:rights to 0..*
everywhere in DCAT-AP.

Conflicting cardinality of the spatial resolution with GeoDCAT-AP #384
Description
Resolution of GeoDCAT-AP revision conflicting with
DCAT-AP 3.0

Motivation
In GeoDCAT-AP, the community agreed on
• For Distribution, spatial resolution [0..1] represents the spatial resolution of the described file.
• For Data Service – spatial resolution [0..*] describes the capabilities of the data service, i.e. in
  which spatial resolutions it can serve data.
• For Dataset – spatial resolution [0..*] describes the spatial resolution of the original data in the
  dataset, i.e. regardless of how it is distributed using distributions.


Proposition
Relax the DCAT-AP 3.0 cardinality of spatial resolution for Dataset to 0..*.

Inclusion of dcat:DatasetSeries into dcat:Catalog #348
Description
How to include a dcat:DatasetSeries directly into a dcat:Catalog? In DCAT-AP 3.0.0,
dcat:DatasetSeries is not a subclass of dcat:Dataset but of dcat:Resource, creating
ambiguity in how to properly include it in a catalog.
Motivation
• An open issue on the topic exist at W3C on DCAT3
• Decision to be taken in autumn 2025 Webinar
Proposition
1. No support, wait for W3C (no release)
2. Introduce a separate r5r:datasetSeries property (equivalent to dcat:dataset or
   dcat:service) (minor release)
3. Replace the use of dcat:dataset and dcat:service with dcat:resource and then it is up to
   the system to adress the expectations. (minor release)
Changes in Checksum class in SPDX 3.0 #402
Description
SPDX 3.0 has been released. DCAT-AP relies on SPDX 2.0. SPDX 3.0 replaces the Checksum class with the Hash class.



Motivation

Specific SPDX problems:
a) the (versionless) URIs refer to the version 2.3 version
b) the SPDX community does not consider RDF representation as cross specification relevant.
c) version 2.3 is not made obsolete

Specific DCAT-AP problem:
Change from version 2.3 to version 3.0 impacts DCAT-AP users without additional benefit.
Generic problem:
DCAT-AP relies on external vocabulary and this vocabulary deprecates the use of the terms used by
DCAT-AP.
